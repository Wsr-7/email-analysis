## 0. 重估前提：F 系列之后哪些原动机已经消失

原 R3/R4 清单（07 §4）制定于 F 系列之前。经过五轮验证迭代，以下事实已改变部分条目的成立基础：

1. **草稿丢失/webview 状态问题已根治**（F1.3 扩展侧持久化 + F3.1 flush 超时 + F4.2 空值语义）——原 U-1"增量渲染"的最大动机消失。
2. **digest 解析五轮验证零故障**（含 ScanSummary、中文、注入文本、多行正文）——原 C-3"NDJSON 化"的健壮性紧迫度下降。
3. **采集诊断已可见**（F1.4 ScanSummary→toast）——原 C-7e"DIAG 协议"的价值被覆盖大半。
4. **recentHours Restrict 修复后拉取已快**（candidateItems 远小于 totalItems）——R4"增量拉取"的收益边际变小。
5. **双 store 同步类 bug 已清零**（meetings 接线、ignored 黑洞等都已修）——B-4"线程唯一真相源"重构的止损价值下降。
6. **用户真实使用反馈已积累**：分析耗时（2-3 分钟/20 封）是体感最强的痛点；会议队列定位（邀请优先）已有明确倾向；安全词表覆盖面被点名。

## 1. 前置元问题 M0（影响多个决策项，请先答）

- 自用：D3 只需词表配置化（你自己能调就行），MIP 可缓；marketplace 素材（截图等）按需；C-3 等通用化改造全缓。

## 2. A 组 · 建议做（高收益、S-M 改动，拍板后进 R3）

### D1 · 分析提速：chunk 并行（原"并行分析"，用户痛点 #1）

- **现状**：chunk 串行，20 封 2 chunk 约 121s，耗时全在模型生成。chunk 间无数据关联（每 chunk 独立合并落盘，F5.4 已验证增量进分类）。
- **方案**：chunk 并发执行，并行度默认 2（做成常量或设置项）；失败/限流沿用既有 429 退避与 F1.2 对账兜底；进度文案改为"已完成 x/N chunk"。
- **收益**：20 封 ≈ 2-3 分钟 → 约 1-1.5 分钟；50+ 封时收益更大。
- **改动范围**：M（app-analysis 并发循环改造 + 进度/取消语义适配 + 单测）。
- **风险**：Copilot 限流概率随并行度上升——并行度 2 温和，退避机制已有。
- **性价比**：★★★★★
- **待拍板**：① 做不做；② 并行度默认 2 可否；③ 是否顺带加设置 `easyMail.draftGeneration: "auto" | "onDemand"`（onDemand 分析时不生成草稿、点击再生成，可再砍约一半耗时——默认 auto 保持现有体验，给你一个提速开关）。

### D2 · 会议队列重定位为"会议邀请"（用户明确倾向）

- **现状**：混合视图（近 2 天日程 + 未响应邀请），你已表态价值在邀请。F 系列已修好显示/详情/排序/按钮。
- **方案**：队列改名 `会议邀请 / Meeting Invites`；未响应邀请为主体默认展开；已接受/组织的未来会议折叠为次级分组（保留可看，不删采集）。响应邀请仍走 Open in Outlook（**不做**插件内 Accept/Decline——COM 可行但误操作风险与测试成本不值）。
- **收益**：功能定位清晰，符合真实用法。
- **改动范围**：S-M（labels + sidebar 分组渲染 + 排序，采集与 store 不动）。
- **性价比**：★★★★
- **待拍板**：① 已接受的未来会议"折叠保留"还是"彻底不显示"；② 插件内直接响应邀请确认不做，同意否。

### D3 · 安全分级配置化（S-1/S-5/hardBlock 可配置合并包）

- **现状**：hardBlockKeywords（F6.5 已扩中英文）、manualConfirmKeywords、分级关键词→级别映射全部硬编码；分级名沿用你公司四级。
- **方案（一期）**：三组词表搬进 VS Code Settings（`easyMail.hardBlockKeywords` / `easyMail.manualConfirmKeywords` / 分级关键词映射），默认值 = 当前硬编码值，语义不变（子串、大小写不敏感）。
- **可选（二期，M）**：读取 MIP 敏感度标签（`msip_labels` MAPI 属性，模式同读 internetMessageId）+ 用户配置"标签名→级别"映射，标签存在时优先于关键词。需真机 Exchange 验证。
- **收益**：一期让你随时按环境调防线；二期给 Exchange 环境权威分级。
- **改动范围**：一期 S-M；二期 M（VBS + digest 字段 + 映射 + 真机验证）。
- **性价比**：一期 ★★★★；二期 ★★★（取决于 M0）
- **待拍板**：只做一期，还是一期+二期。

### D4 · dueDate 结构化（B-2b）

- **现状**：期限信息埋在 summary/suggestedAction 文本里，不可排序、不可比较。
- **方案**：output schema 增加可选 `dueDate`（ISO 日期或空），normalize 校验非法值置空；sidebar 的 Must Handle Today / Waiting for Me 分类内按 dueDate 升序排（无期限的排后），过期/今天到期红色标注；workbench 详情显示期限字段。
- **收益**：分诊核心动作（先处理最紧急的）从"读文本"变成"看排序"。
- **改动范围**：S-M（schema + prompt + normalize + 两处渲染 + 单测）。
- **性价比**：★★★★
- **待拍板**：做不做；过期标红的判定用本地日期即可，同意否。

### D5 · Webview CSP 加固（U-2）

- **现状**：三个 webview（sidebar/workbench/guide）**均无 Content-Security-Policy**，XSS 防线只靠 escapeHtml——邮件正文是不可信输入，单层防御不符合纵深原则。
- **方案**：按 VS Code 官方模式加 CSP meta（默认拒绝 + script nonce + 样式内联白名单），inline script 挂 nonce。
- **收益**：安全基线补齐，一次到位。
- **改动范围**：S-M（三个 render 模板 + nonce 生成 + 单测断言 CSP 存在）。
- **性价比**：★★★★（安全项，成本低）
- **待拍板**：做不做（规划者强烈建议做）。

## 4. C 组 · 建议延后或不做（附理由，如无异议不再讨论）

| 原条目 | 建议 | 理由 |
|---|---|---|
| U-1 增量渲染 | **不做**；若刷新闪烁/滚动位置丢失让你在意，可做轻量版"刷新后保持滚动位置"（S 级） | 最大动机（草稿丢失）已根治；全量 DOM patch 化改动 L 级、回归风险高 |
| B-1 tags 化与过滤视图 | **延后** | schema+prompt+UI 全动（L 级）；五轮验证你未提出过滤需求，属没有需求支撑的架构改造 |
| B-4 线程唯一真相源 | **延后** | 纯内部重构（M-L），无用户可见收益；双 store 同步 bug 当前已清零，等再出同类 bug 时作为根治手段再启 |
| C-3 digest NDJSON 化 | **延后** | 解析五轮零故障；等未来真要做增量拉取/附件传输等格式扩展时一并重构 |
| C-7e DIAG 协议 | **不做** | ScanSummary + RestrictFilter + toast 已覆盖诊断需求 |
| U-3 密度改造 | **不做** | 主观样式大改；对具体页面的具体不满走单点反馈更划算 |
| R4 增量拉取 | **延后观察** | Restrict 修复后拉取已快；若你在超大邮箱上仍感慢，再评估 anchor 增量方案 |
